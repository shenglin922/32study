# STM32 工业数据采集终端（FreeRTOS + Modbus RTU）

基于 **STM32F103C8T6** 与 **FreeRTOS** 的工业级温度采集与通信终端。系统采用多任务抢占式调度架构，实现 DS18B20 高精度单总线测温、本地超温报警控制、Modbus RTU 从机通信（功能码 `0x03` / `0x06`）以及基于水位线监测的任务栈内存调优，后续将接入 W25Q64 实现参数掉电存储与历史环形日志。

---

## 硬件配置与引脚分配

* **主控芯片**：STM32F103C8T6（ARM Cortex-M3，72MHz，20KB RAM / 64KB Flash）
* **开发环境**：VS Code + Keil MDK5 + STM32CubeMX + HAL 库
* **外设与引脚映射**：

| 模块 / 接口 | 芯片引脚 | 通信参数 / 电气特性 | 功能说明 |
| :--- | :--- | :--- | :--- |
| **USART2 (Modbus)** | `PA2` (TX) / `PA3` (RX) | `115200, 8N1` (HEX) | Modbus RTU 从机通信接口（中断接收 + 环形缓冲区） |
| **USART1 (调试口)** | `PA9` (TX) / `PA10` (RX) | `115200, 8N1` (ASCII) | 输出系统状态、温度快照及 FreeRTOS 栈/堆水位监控日志 |
| **DS18B20 传感器** | 单总线 GPIO | 开漏输出 + 外部上拉 | 采集环境温度（定点放大 100 倍处理） |
| **板载状态 LED** | `PC13` | 推挽输出（低电平有效） | 超温报警指示灯（温度 $\ge$ 阈值时点亮） |
| **TIM2 定时器** | 内部定时器 | 1MHz 计数（`1us` 分辨率） | 为 DS18B20 单总线时序提供无中断微秒级延时 |
| **W25Q64 Flash** | SPI 接口（待接入） | SPI Mode 0/3 | 用于报警阈值掉电保存与历史温度环形存储 |

## 系统软件架构（FreeRTOS）

系统基于 CMSIS-RTOS 封装层运行 3 个独立任务，通过**优先级抢占 + `osDelay` 主动阻塞让权**实现并发调度：

| 任务名称 | 优先级 | 调度周期 / 触发方式 | 优化后栈大小 | 核心职责 |
| :--- | :--- | :--- | :--- | :--- |
| **`ModbusTask`** | 高 (`AboveNormal`) | 周期轮询 `uart2_rb` (`osDelay(2)`) | `128 Words` (`512 B`) | 解析 Modbus RTU 报文，加锁读取最新温度/状态或修改报警阈值并组帧回复 |
| **`TempTask`** | 中 (`Normal`) | 周期采集 (`osDelay(800)`) | `128 Words` (`512 B`) | 触发 DS18B20 转换并等待 800ms，读取温度后加锁更新全局寄存器与 `PC13` 报警灯 |
| **`CliTask`** | 低 (`Low`) | 定时上报 (`osDelay(3000)`) | `192 Words` (`768 B`) | 统计各任务历史最小剩余栈空间与系统剩余堆内存，通过 `USART1` 打印遥测日志 |

### 并发与数据同步设计
* **共享寄存器互斥保护（`g_reg_mutex`）**：`g_temp_x100`（当前温度）、`g_dev_status`（设备/报警状态）与 `g_alarm_th_x100`（报警阈值）由互斥锁保护，防止 `TempTask` 更新多变量到一半时被高优先级的 `ModbusTask` 抢占，导致发出“温度已超标但状态位仍为正常”的一致性撕裂（此类逻辑错误无法被帧尾 CRC16 检出）。
* **中断与任务解耦**：`USART2` 接收中断回调函数（`HAL_UART_RxCpltCallback`）仅将单字节压入 `uart2_rb` 并重装接收中断，耗时控制在微秒级，帧解析与 CRC16 计算全部交由 `ModbusTask` 在任务上下文完成。

## Modbus RTU 协议说明

* **默认从机地址**：`0x01`
* **支持功能码**：`0x03`（读保持寄存器）、`0x06`（写单个保持寄存器）
* **保持寄存器映射表**：

| 寄存器地址 | 变量名 | 读写属性 | 数据格式与说明 |
| :--- | :--- | :--- | :--- |
| `0x0000` | `g_temp_x100` | 只读 (`0x03`) | 当前温度值 $\times 100$（有符号 16 位整型，如 `2593` 表示 `25.93°C`） |
| `0x0001` | `g_dev_status` | 只读 (`0x03`) | 设备运行状态：`0` = 正常，`1` = 高温报警，`2` = 传感器断开/异常 |
| `0x0002` | `g_alarm_th_x100` | 读写 (`0x03`/`0x06`) | 高温报警阈值 $\times 100$（默认 `3000`，即 `30.00°C`） |

* **常用测试报文（HEX）**：
  * 读取全部 3 个寄存器：`01 03 00 00 00 03 05 CB`
  * 修改报警阈值为 `20.00°C` (`2000` / `0x07D0`)：`01 06 00 02 07 D0 2B A6`

## 遇到的疑问
为什么在中断里只存数据，不处理命令？---在中断里花的时间越长，丢数据和卡死的概率越大

完整链路：
字节到达 PA10，串口硬件收到 1 个字节，触发 USART1 中断，CPU 跳到 USART1_IRQHandler，里面调用 HAL_UART_IRQHandler，HAL 把字节存进 rx_byte，再调用回调函数 HAL_UART_RxCpltCallback回调里只做两件事：rb_write 把字节放进环形缓冲区，重新开启 HAL_UART_Receive_IT（不重开就只能收 1 个字节），主循环用 rb_read 一个个取出字节，交给 cmd_feed_byte，不是 \n 的字符存进 line_buf，同时检查长度防止越界，遇到 \n，补上 \0 变成合法字符串，进入 process_command，normalize_cmd 去掉多余空格、统一大写，遍历命令表，用 strcmp 逐条比较，匹配后通过函数指针调用对应的处理函数，没匹配回 ERROR，cmd_led_on 调用 HAL_GPIO_WritePin 把 PC13 拉低，灯亮，回复 OK

开漏输出没接传感器总线悬空，会被误判为有传感器

温度换算用定点整数x100，避免浮点

拔线测试中发现悬空总线误判读出0.00°，于是增加总线释放检测修复

CRC8本质是做除法取余数，全0数据的crc也是0 ，所以需要额外检查保留字节 0xFF

不加互斥锁、温度跳变时被抢占会发生什么:不仅单变量可能出现高低字节撕裂，更常见的是多变量状态不一致（温度已超标更新，但报警状态位尚未更新就被抢占发出）；且由于帧尾 CRC16 是在组帧完成后现算的，上位机 CRC 校验依然会通过，造成难以察觉的静默数据错误

cmsis_os:ARM 制定的 RTOS 统一接口转接头，将 FreeRTOS 原生 API 封装为 os 前缀函数

是不是优先级高的执行完再给优先级低的？:RTOS 任务是死循环，永远不会“执行完”，而是靠“主动调用 osDelay 睡觉让权”和“高优先级闹钟响起时直接抢占插队”来轮流使用 CPU
